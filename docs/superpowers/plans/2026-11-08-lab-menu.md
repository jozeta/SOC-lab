# Lab Menu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `deploy-soc-lab.sh` lets you pick a lab (SOC, network forensics, pentest, DevSecOps) and a size (small/medium/large) from a menu or flags, and builds that lab.

**Architecture:** One data file, `lib/labs.sh`, defines every VM's spec and role and every lab's VMs per size, client count and kind, purpose text and time weights; small query functions read it. `lib/menu.sh` parses flags and runs the numbered menu and summary. The deploy script sets `VM_ENABLED`/`NUM_CLIENTS` from the chosen lab and keeps its existing `is_enabled`-gated stages. New labs add templates and seed roles.

**Tech Stack:** bash 4+ (Homebrew), Multipass 1.16.4, cloud-init, Python 3 stdlib (`seed/labdata.py`), `unittest` + PyYAML + ShellCheck for tests.

**Spec:** `docs/superpowers/specs/2026-11-08-lab-menu-design.md` (approved 2026-11-08)

## Global Constraints

- bash 4+ (Homebrew bash), Apple-silicon macOS, arm64 Ubuntu 24.04 images; every app a lab installs must exist for arm64.
- All deploy output through `say` / `lib/progress.sh`; the menu runs before the live panel starts.
- Never run `multipass` commands concurrently; polling stays serial; never redirect `multipass exec` output to `/dev/null`.
- Templates keep passing `tests/test_templates.py` (placeholders filled, valid cloud-config, `bash -n`, ShellCheck).
- Every lab's large size: at most 48 GB RAM allocated (computed from the specs; a test enforces it).
- One lab at a time: a lab is running if any known lab VM shows in `multipass list`.
- Planted weaknesses are exercises: never "fix" them. Keep the lab on the Multipass NAT network.
- `lab-info.sh`, `lab-doctor.sh`, README (architecture table, resource totals), CLAUDE.md and CHANGELOG (Unreleased) stay in sync with every new VM and app.
- Case PCAPs: fetched inside `arkime` only, from a pinned list (URL + SHA-256), kept in their password-protected zips.

## Review Focus

1. A lab already running without a state file (VMs from before this change, or a failed deploy): the deploy must refuse and name `teardown-soc-lab.sh` (test in Task 3).
2. Bad flag values (`--lab foo`, `--size xl`, `--lab` without a value): exit 2 with the valid values listed (test in Task 2).
3. No terminal and no flags (CI, a pipe): exit 2 naming `--lab`/`--size`, nothing launched (test in Task 2).
4. A lab without `siem` or `dc01` (pentest, DevSecOps): no template tries to install a Wazuh agent or join a domain, and no stage pushes Wazuh rules (tests in Tasks 3 and 4).
5. A Mac with less RAM than the lab needs: the summary shows a warning and the confirmation defaults to No (test in Task 2).

### Task 2: Flags, menu and summary (`lib/menu.sh`)

**Files:**
- Create: `lib/menu.sh`
- Test: `tests/test_menu.py`

**Interfaces:**
- Consumes: everything in Task 1.
- Produces:
  - `parse_lab_args "$@"` sets globals `LAB`, `SIZE`, `ASSUME_YES` (0/1), `LIST_ONLY` (0/1), `DRY_RUN` (0/1). It accepts `--lab X`, `--size Y`, `--yes`, `--list`, `--dry-run` and `--help`. Bad values exit 2 with `valid labs: soc forensics pentest devsecops` / `valid sizes: small medium large`.
  - `choose_lab` fills any of `LAB`/`SIZE` still unset through the menu, reading the terminal. It exits 2 with a message naming `--lab`/`--size` when stdin is not a terminal (`[ -t 0 ]`, overridable for tests with `LAB_MENU_TTY=1`).
  - `print_lab_list` (for `--list`): every lab, its purpose and the totals for each size.
  - `print_lab_summary <lab> <size>`: every VM with its `vm_role`, the client count and kind, the `lab_totals`, `≈N min`, and a RAM warning line starting `WARNING: this lab needs` when the needed RAM + 8 GB headroom exceeds the host RAM (`sysctl -n hw.memsize`, overridable with `LAB_HOST_RAM_GB`).
  - `confirm_lab` → returns 0 on `y`/`yes`; the default (Enter) is No; `b` goes back to the size choice; `q` exits 0 without deploying. Skipped when `ASSUME_YES=1`.
- The menu's screens: lab list (number, title, purpose, the RAM range from small to large) → size list (each with VM count, clients, RAM, ≈time) → summary → confirm. `b` goes back and `q` quits on every screen.

- [ ] **Step 1: Write the failing tests** in `tests/test_menu.py`. They run a tiny driver (`bash -c 'source lib/labs.sh; source lib/menu.sh; parse_lab_args "$@"; choose_lab; print_lab_summary "$LAB" "$SIZE"; confirm_lab && echo CONFIRMED' _ <args>`) with `input=` piped in:
  - `test_flags_skip_the_menu`: `--lab pentest --size small --yes` with no stdin prints the summary and `CONFIRMED`
  - `test_bad_lab_value`: `--lab foo` exits 2, and the output contains `valid labs: soc forensics pentest devsecops`
  - `test_bad_size_value`: `--size xl` exits 2 with `valid sizes: small medium large`
  - `test_missing_value`: `--lab` alone exits 2
  - `test_no_terminal_no_flags`: no args, stdin not a TTY: exits 2, the output names `--lab` and `--size`, and `CONFIRMED` is absent
  - `test_menu_choices` (`LAB_MENU_TTY=1`): input `3\n1\ny\n` gives a summary of pentest small and `CONFIRMED`
  - `test_menu_back_and_default_no`: input `1\nb\n2\n\n` (back to the lab list, pentest… then Enter at confirm) gives no `CONFIRMED`
  - `test_ram_warning`: `LAB_HOST_RAM_GB=16`, `--lab soc --size large`: the summary contains `WARNING: this lab needs`, and the confirmation still defaults to No
  - `test_summary_lists_every_vm`: every name from `lab_vms forensics medium` and `client01..03` appears in the summary
  - `test_list_flag`: `--list` prints all four titles and three sizes each, then exits 0
- [ ] **Step 2: Run them:** `python3 -m unittest tests.test_menu -v`. Expected: FAIL.
- [ ] **Step 3: Write `lib/menu.sh`** with the functions above. Plain `printf` is fine here: it runs before the progress panel exists.
- [ ] **Step 4: Run them:** `python3 -m unittest discover -s tests -v`. Expected: PASS. Also run `shellcheck lib/menu.sh lib/labs.sh`. Expected: clean.
